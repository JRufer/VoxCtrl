**Fixed: the voice-command pill not appearing on desktops without
compositing** ([#187](https://github.com/JRufer/VoxCtrl/issues/187)). On a
desktop with no compositing manager (for example Xfce with *Enable display
compositing* unchecked), 0.8.7 began building the overlay window on first use
and hiding it again whenever it had nothing to show, so that an idle overlay
could not sit on screen as a black rectangle. The command pill is announced to
the overlay the instant a command fires, which is just before that window gets
built or shown — so the window that appeared had missed the announcement and
came up blank. "Show overlay on voice command trigger" looked like it had
stopped working. The pill is now re-sent once the window is actually up, with
however much of its time is left. Desktops with a compositor were never
affected and are unchanged.

**Fixed: voice commands ignored when the transcript starts with a filler
word** ([#186](https://github.com/JRufer/VoxCtrl/issues/186)). VoxCtrl
recognises a mis-heard wake word ("hey fox", "box control", "walks control")
as well as a clean one, but it only looked for it in the first word or two of
the transcript. Speech engines differ in how much they tidy up what they hear:
one that writes out the lead-ins real speech is full of — "Okay, hey Fox,
notes…", "So hey box notes…" — pushed the wake word past where VoxCtrl was
looking, and the command was typed out as dictation instead of being run. The
same words through an engine that drops the lead-in worked, which is why this
looked like a difference between Whisper and Parakeet. VoxCtrl now looks for a
mis-heard wake word across the opening few words rather than only the first.

Ordinary dictation is unaffected: away from the start of a sentence the match
has to be closer, so phrases like "I lost control" are still just words, and
the wake word must still be followed by the name of an output target before
anything is treated as a command.
